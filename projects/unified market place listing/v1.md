# v1: Build Brief

This is the build brief for the coding agents working on version 1. Read it first. It defines what to build, in what order, and how to tell when a piece is done.

Two companion documents. `product_spec.md` explains the product, and you rarely need it while coding. `architecture.md` holds the full schema, the canonical JSON shape, the error envelope, the adapter interface, and the stack. Where this brief and `architecture.md` disagree about a contract, `architecture.md` wins. Where they disagree about scope, this file wins.

---

## Hard constraints

These are not negotiable and they are not stylistic preferences. Code that breaks one of them does not merge.

1. The rules engine is deterministic code. Never an LLM call. If a check can be written as code, it is code.
2. Nothing reaches an adapter without passing validation. No bypass flag. Not even in tests.
3. Every model response is parsed into a Pydantic model before any other code reads it.
4. Every failure returns the shared error envelope from `architecture.md`. Do not invent a second error shape in a module.
5. Tenant scoping happens in the repository layer. Application code cannot write an unscoped query.
6. Adapters own their marketplace's quirks. No Amazon field name leaks into shared code.
7. Every agent run writes an audit row with model name, input tokens, output tokens, cost, and the error report if it failed.
8. Nothing publishes without an approval record. There is no auto-publish path in v1.

## What v1 ships

| Area          | In v1                                                                                    |
| :------------ | :--------------------------------------------------------------------------------------- |
| Marketplaces  | Amazon and Flipkart, both fully implemented against the shared adapter interface         |
| Import        | CSV and Excel bulk upload, plus single-product manual entry                              |
| Generation    | Content agent, keyword agent                                                             |
| Validation    | Rules engine plus image checks, returning the structured envelope                        |
| Review        | Human approval gate with per-row accept and reject, reject reasons fed back to the agent |
| Publish       | Push to one or both marketplaces with per-field result reporting                         |
| Analytics     | Combined performance view across both marketplaces                                       |
| Auth          | Invite-only onboarding, JWT sessions, encrypted marketplace credentials                  |
| Brand context | Tone, glossary, banned terms, captured in onboarding, retrieved at generation time       |
| Media         | S3 storage for images, CSVs, and batch artifacts                                         |
| Jobs          | Redis and ARQ for bulk import and agent runs, with per-job status                        |

## What v1 does not ship

Do not build these. Do not scaffold them, do not leave hooks for them, do not name a variable after them. They are Phase 2 and Phase 3, and building them now costs time and creates dead code.

- Version history for listings
- Sales attribution and revenue analytics
- The optimization agent that proposes edits to live listings
- Competitor price or ranking signals
- Auto-publish at any confidence level
- Real-time inventory or order sync
- Image retouching or background removal as an editing service. The pipeline flags problems and suggests fixes only
- A public signup flow
- Our own marketplace taxonomy

## Build order

The dependency order matters. Work that starts before its dependency lands will be thrown away.

```
1. Data and persistence       schema, migrations, repository layer with tenant scoping
   │
2. Auth and identity          invite flow, JWT sessions, account creation
   │
3. Marketplace auth           OAuth for both marketplaces, token encryption, refresh
   │
4. Data bridge                CSV and Excel parsing, entity extraction, canonical JSON
   │
5. Validation                 rules engine, category rule loading, error envelope
   │
6. AI generation              LangGraph graph, the four agents, brand voice retrieval
   │
7. Execution                  adapter interface, two implementations, per-field results
   │
8. Task orchestration         queue wiring, batch fan-out, job status
   │
9. Web UI                     onboarding, import, review workspace, analytics
```

Steps 1 through 3 are sequential and everything depends on them. After step 4, validation and generation can run in parallel, and the two adapters can be built by two agents simultaneously because they only share the interface.

The fastest path to something demonstrable is steps 1, 2, 4, 5, 6, and a thin slice of 9. That gives a working pipeline with no marketplace connection, which is the CSV-only path. It is useful on its own and it unblocks the adapters, which are blocked on marketplace approvals rather than on code.

## Per-module acceptance criteria

Each module is done when these hold. Write these as tests, not as manual checks.

### Data and persistence

- The full schema from `architecture.md` exists as migrations and applies to an empty database with no manual steps.
- A query that omits `workspace_id` fails, or cannot be constructed. Prove it with a test that asserts the scoping is enforced.
- `marketplace_payloads` rows reference a variant, never a product.
- Soft delete is respected by default reads.

### Auth and identity

- An invite token can be consumed exactly once. A second attempt fails.
- A consumed token cannot create a second account.
- Every authenticated request resolves to a workspace, and the resolved workspace drives tenant scoping.
- Password storage is hashed with a current algorithm.

### Marketplace auth

- Both marketplaces complete an OAuth round trip in a sandbox or staging environment.
- Tokens are encrypted at rest. Reading the raw database column does not reveal a usable token.
- An expired token refreshes once and retries. A second failure marks the connection as needing attention.
- Disconnecting a marketplace does not delete published listing records.

### Data bridge

- A CSV upload maps to the canonical JSON from `architecture.md`.
- The two real agency files, the Amazon macro workbook and the Flipkart export, parse without manual intervention.
- Unparsable rows fail individually with a row number and a reason. They do not abort the batch.
- A single product with variants produces one product and N variants, not N products.

### Validation

- Category rules load per marketplace and per category.
- A title over the Amazon limit fails with `TITLE_TOO_LONG` and the exact limits in the message.
- A banned term on Flipkart on a field passes on Amazon. Marketplace rules never bleed into each other.
- Every failure carries a dotted `field` path that the correction agent can write back to.
- The rules engine has zero model calls. Verify by running it with the model client stubbed to raise.

### AI generation

- The graph runs end to end and produces canonical JSON that validates against the Pydantic model.
- Brand voice chunks are retrieved and present in the prompt. Assert on the assembled prompt, not on the output.
- A validation failure routes to the specific agent that produced the failing field, not to all agents.
- Retries stop at 3 and then block, surfacing the error report.
- Invalid JSON from the model is repaired or retried, never persisted.

### Execution

- Both adapters implement the full interface. Neither raises `NotImplementedError`.
- A partial publish returns exactly which fields failed plus the marketplace's raw error string.
- Retrying a partial publish does not re-push fields that already succeeded.
- Rate limits trigger backoff inside the adapter with no agent involvement.
- A SKU conflict surfaces to the user rather than retrying forever.

### Task orchestration

- A bulk import returns a job id immediately and does not block the request.
- Batch concurrency stays inside the per-marketplace ceiling.
- One failing row does not stop the batch, and the summary reports per-row outcomes.
- A failed row is re-runnable with identical input.

### Web UI

- Onboarding collects profile type, details, brand context, and marketplace connection in that order.
- The review workspace shows generated content beside the per-field validation errors.
- A rejection carries a reason back to the generation step.
- Bulk import shows per-row status and lets the user retry failed rows.
- A seller with no connected marketplace can complete the flow and download listing files.

## Definition of done

A task is done when all of these hold.

1. Tests cover the acceptance criteria for that module and they pass.
2. The module writes and reads the canonical shapes, with no local variants of them.
3. No adapter field name, no marketplace-specific constant, and no prompt text appears outside its owning module.
4. Errors use the shared envelope.
5. The audit row is written on every agent run.
6. No secrets in the repository. Marketplace credentials come from encrypted storage or the secrets manager.
7. The change does not leave a hook, flag, or scaffold for a Phase 2 feature.

## Things that will trip you up

Recorded because they cost time when rediscovered.

**A validation error belongs to a variant, not a product.** A Large Navy shirt failing image compliance is a variant-level failure. Getting this wrong means the audit trail cannot name what actually failed, and the correction loop has no valid target to write to.

**`category_path` and the browse node are different things.** `category_path` is human-readable and the AI uses it as context. The browse node or category id is a machine coordinate that only the adapter cares about. Do not try to derive one from the other. The adapter resolves the coordinate, the AI reads the path.

**Amazon and Flipkart rate limits are per endpoint, not per account.** A global throttle will either be too slow to be useful or will still trip. Track limits per endpoint per marketplace inside the adapter.

**Flipkart requires category and brand mapping to its own taxonomy before a product push will succeed.** Treat this as a prerequisite step in the adapter, not as an error to handle at publish time.

**The rules engine must be runnable with no network.** If a test run shows it making a model call, the check belongs in code, not in a prompt.

**Batch concurrency is bounded per marketplace, not globally.** A global ceiling either starves the fast marketplace or overloads the slow one.

**Resolution, format, and aspect ratio are deterministic checks.** Do not send an image to the vision model to learn something PIL can answer. It costs money and adds latency for no gain.
